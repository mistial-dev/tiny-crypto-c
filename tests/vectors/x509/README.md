# X.509 test corpus

Certificates, CRLs, PKCS#7 bundles and CSRs for exercising the X.509 parser:
old and new, real and synthetic, valid chains and deliberately broken ones.
Everything vendored from upstream is checked in unmodified (`.gitattributes`
marks `tests/vectors/**` as binary so CRLF, "Bag Attributes" prefixes and
trailing junk survive). Derived files say so, and the tool that produced them
is in `tools/`. Assembled 2026-09-06.

Private keys are never checked in. Expect the GSA ICAM and PIV demo files to
carry OpenSSL "Bag Attributes" text before the PEM block: a parser has to skip
leading text (RFC 7468 §2 allows it).

## Sources, licences and checksums

### `rfc/`

* `rfc5280_cert1.cer`, `rfc5280_cert2.cer`, `rfc5280_cert3.cer`, `rfc5280_CRL.crl`
  and `RFC3280_cert*.cer`: the DER for RFC 5280 / RFC 3280 Appendix C, as
  published by NIST at <https://csrc.nist.gov/projects/pki-testing> (RSA
  self-signed CA, RSA end entity, DSA end entity, CRL).
* `rfcNNNN_MM.*.pem`: PEM blocks extracted verbatim from the RFC text
  (`MM` is the ordinal of the PEM block in the RFC). Public keys and
  attribute certificates are included where the RFC has them.
  * RFC 7468: GnuTLS ECDSA CA, sha1WithRSA `CN=Atlantis`, `X509 CERTIFICATE`
    legacy label, CRL, attribute certificate, `CERTIFICATE CHAIN`.
  * RFC 8410 §10.1: Ed25519 self-signed certificate.
  * RFC 9802: HSS/LMS, XMSS and XMSS^MT CA certificates.
  * RFC 9881: ML-DSA-44/65/87 self-signed certificates and public keys.
  * RFC 9909: SLH-DSA-SHA2-128s certificate and public key.
  * RFC 9919: ECDSA P-521 CA, end entity (IDN CN) and OCSP responder.
  * RFC 9935: ML-KEM-512/768/1024 certificates signed with ML-DSA, and keys.
  IETF documents; Trust Legal Provisions apply.

NIST test suites are US Government works, public domain.

* `pkits/certs`, `pkits/crls`, `pkits/certpairs` are the archive's directories
  as-is (`.cp` files are X.509 `crossCertificatePair` structures, not
  PKCS#7). The PKCS#12 and S/MIME directories were left out. The 4.x test
  descriptions are in the PKITS PDF in the Reference Library.
* `pdts/`: `End Entity Certs` and `Trust Anchor Certs` renamed to
  `end_entity_certs` / `trust_anchor_certs`; the file names are unchanged.
* `x509tests_2001/testNN/`: the `.crt`/`.crl` files of each test with spaces
  in file names replaced by `_`. The `.crtx` files (PKCS#8 private keys) and
  the `.p7m`/`.p12` files were dropped. These are 2000-era 1024-bit RSA,
  sha1WithRSA, v3 certificates with the older NIST PKI profile.

### `icam/`

GSA ICAM test-card artefacts from
<https://github.com/GSA/gsa-icam-card-builder> (`cards/ICAM_Card_Objects`),
CC0 1.0 / US public domain. Copied without the `.p12` key files; `" - "` and
spaces in card file names became `_`.

* `ca/roots/`: the ICAM Test Card Root CA plus 36 deliberately faulty roots
  (`01_ICAM_Invalid_CA_Signature` ... `36_ICAM_Invalid_CRL_Signer`).
* `ca/bridge/`: the Bridge CA, its 36 cross-certificates to the faulty roots,
  and `Intermediate_Bridge_Certs.p7b`.
* `ca/crls/`: one CRL per faulty CA (several intentionally malformed or
  expired: `ICAMExpiredCRL.crl`, `ICAMInvalidCRLSignature.crl`, ...).
* `ca/aia/`, `ca/sia/`: `certsIssuedTo*.p7c` / `certsIssuedBy*.p7c` bundles
  as served from the AIA/SIA URLs. Five `.p7c` files are 37-byte empty
  SignedData structures.
* `ca/signers/`: content-signing, OCSP responder and SM certificate signer
  certificates (RSA-2048, P-256, P-384; gen 1-2 and gen 3; expired, revoked,
  invalid-signature variants).
* `cards/NN_*/`: the PIV Authentication, Digital Signature, Key Management,
  Card Authentication and Key History certificates for each of the 55 ICAM
  test-card directories, including the "tampered", "expired", "not yet valid",
  "revoked", FASC-N/UUID mismatch and 2160-byte large-certificate cards.

### `piv/`

* `sd33/cardNN_{piv_auth,card_auth}_cert.der`: the DER certificates gunzipped
  out of the `5FC105`/`5FC101` PIV data objects captured from NIST Special
  Database 33 test cards (ID-One PIV 2.4) by the PIV Subcommittee VCI vector
  project (`~/Projects/PIV Subcomittee/sm_vci_vectors`). The raw objects are
  in `../piv/sd33/`.
* `yubikey/`: RSA-1024, RSA-3072 and P-384 certificates generated on a
  YubiKey for PIV slots 9a/9c/9d/9e (PIV Subcommittee `osdp-piv-latex`).
* `piv_auto_demo/`: root, RSA-2048 intermediate, P-256 CVC signer, card
  authentication and content-signing certificates used by the PIV Auto
  simulator (derived from GSA card-builder material).

### `eid_testbeds/`

From <https://github.com/eID-Testbeds/server> (`eidsrv-testbed-runner/src/main/resources`),
Apache-2.0 (`LICENSE` included). `csca/`: the testbed CSCA
(`CERT_ECARD_CSCA_1.DER`, ecdsa-with-SHA384), document signer `DS_1_B`,
master-list / black-list / defect-list signer certificates (DER and PEM), a
signed CSCA master list and two black lists as CMS SignedData
(`MASTERLIST_*.DER`, `BLACKLIST_*.DER`). `CERT_ECARD_DS_1_A.DER` is
deliberately corrupt: OpenSSL fails at the issuer name with "Error in
encoding". `tls/`: the testbed's RSA-2048, ECDSA and DSA TLS server,
encryption and client-authentication certificates for the eID-ACME test
hosts, self-signed or under `testbedCA.pem`.

### `web/`

`chain_<host>.pem` is exactly what the server sent in its TLS Certificate
message (`openssl s_client -showcerts`, OpenSSL 3.6.3, 2026-09-06), leaf
first. `manifest.json` records host, per-certificate subject/issuer/
algorithm/key/validity and OpenSSL's verify result against the system store.
Hosts were chosen for variety:

* badssl.com's deliberately broken endpoints (expired, wrong host,
  self-signed, untrusted root, revoked, incomplete chain, sha1 intermediate,
  no CN, no subject, 1000 SANs, RSA-8192, ECC P-384, long subdomains,
  ...). `10000-sans` could not be fetched: OpenSSL rejects the handshake
  message as too large.
* CA demonstration sites for Google Trust Services, Amazon Trust Services,
  Let's Encrypt (valid/expired/revoked under X1 and X2), DigiCert
  (`*.chain-demos.digicert.com` per root), Sectigo/Comodo, GlobalSign
  (`valid/revoked/expired.rN.roots.globalsign.com`), GoDaddy/Starfield and
  SSL.com.
* Large operators, US federal (`*.gov`, `*.mil`, DISA CRL host), national
  and regional CAs across Europe and Asia, security vendors, PACS and smart
  card industry sites, and open-source project sites.

216 chains verify, 19 are expired, 2 have incomplete chains, 2 are
self-signed. Signature algorithms seen: sha256WithRSA 446, ecdsa-with-SHA384
134, sha384WithRSA 56, ecdsa-with-SHA256 21, sha512WithRSA 11, sha1WithRSA
10 (roots).

### `ct/`

`get-entries` samples from eight RFC 6962 logs listed as usable in Google's
`log_list.json` (`log_list_v3.json` is that list, `sth_*.json` the signed
tree heads at fetch time): Google Argon2026h2 and Xenon2026h2, Cloudflare
Nimbus2026, DigiCert Wyvern2026h2 and Sphinx2026h2, Sectigo Elephant2026h2
and Tiger2026h2, TrustAsia log2026a. For each log the first 16 entries, 16
from the middle and 16 from the tail were kept. `entries.json` has one record
per entry (log, index, timestamp, entry type, chain) referencing
`certs/<sha256>.der`; a precert entry's `precert` is the full precertificate
with the poison extension, an x509 entry's `leaf` is the certificate. Chain
certificates are shared between entries, hence the deduplication.

### `limbo/`

<https://github.com/C2SP/x509-limbo>, Apache-2.0 (`LICENSE`), commit
`3f8cba420e90322223486086054401189b7b320e` (2026-09-03). The upstream
`limbo.json` (SHA-256
`563805f46937ad25ac9d4e41341c414070aced32a22294821b5c5fe526e2c52d`, 39 MB,
9793 testcases) is not vendored; `tools/limbo_subset.py` splits it into:

* `limbo-core.json`: all 221 non-`bettertls::` testcases, verbatim:
  `rfc5280::` (109), `webpki::` (56), `pathological::` (11), `pathlen::`
  (13), `crl::` (8), `rfc9881::` (6 ML-DSA), `cve::` (3), `online::` (14),
  `invalid::` (1). 111 expect FAILURE, 110 SUCCESS.
* `limbo-bettertls-sample.json`: a seeded random sample of 100 SUCCESS + 100
  FAILURE cases from the 9572-case Netflix bettertls name-constraints suite.

Both keep the upstream schema (`limbo-schema.json`): `peer_certificate`,
`untrusted_intermediates`, `trusted_certs`, `validation_time`,
`expected_result`, `expected_peer_name`, ...

### `synthetic/`

Produced by `tools/generate_x509_vectors.py` (OpenSSL 3.6.3, 2026-09-06).
Rerunning it makes a fresh PKI, so the files here are the frozen output;
`manifest.json` lists every file with `kind`, `expect`, `reason`, SHA-256,
issuer chain, and what OpenSSL itself said (`openssl`, `openssl_verify`).
`expect` is:

* `parse`: well formed; where a chain is given it validates.
* `parse-only`: well formed DER (or at worst BER a lenient parser accepts)
  but semantically wrong: expired, weak, violates a RFC 5280 MUST or a path
  rule, stale signature after a TBS edit, etc.
* `reject`: a strict DER parser must refuse it.

Where OpenSSL is more lenient than `expect` says (it accepts BER lengths,
trailing garbage, malformed times and several SPKI oddities), `manifest.json`
shows `"openssl": "parsed"` next to `"expect": "reject"`; where it is
stricter, `"openssl": "error: ..."` next to `parse-only`.
